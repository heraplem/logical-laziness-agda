\section{Case Studies}\label{sec:case-study}

To show that the \transCname{} and \transDname{} work in practice, we conduct
some case studies by manually applying these translation strategies on classical
Haskell functions and implementing all translated functions in
Curry~\cite{curry-lang}. These examples include appending lists, insertion sort,
and Okasaki's banker's queue~\cite{purely-functional}. We use the KiCS2 Curry
compiler~\cite{kics2} to test these implementations. We discuss the details of
our implementation in this section.

In addition, we evaluate the performance of translated logical demand functions.
Our results show that, although there are slowdowns compared with the
specialized demand translation of Xia \textit{et al.}~\cite{demand-semantics},
they achieve acceptable performance despite being much simpler. All the code of
our case studies can be found in our publicly-available artifact.\ly{TODO:
  link.}

\paragraph{Foundations.}

We begin by building a framework for representing the logical clairvoyance
semantics and the logical demand semantics in Curry.

We show key definitions of this framework in \cref{fig:curry-foundations}. The
\cdc{T} datatype represents a value whose evaluation may be
skipped~(\cdc{Undefined}) or evaluated~(\cdc{Thunk}). The \cdc{thunk} combinator
uses Curry's nondeterministic choice operator to either skip an effectful
computation~(represented by the applicative functor \cdc{f}) or run it.
% The \cdc{with} combinator pushes an effectful computation through a \cdc{T},
% yielding \cdc{Undefined} if no value is present.

We represent approximation types using the \cdc{Approx} typeclass. The typeclass
contains an \cdc{<~} operator, which indicates its left-hand operand
approximates its right-hand operand. The other method, \cdc{approx}
nondeterministically returns a value that approximates its argument. We include
a default implementation of \cdc{approx} using free variables, but a specialized
implementation can be much faster. The \cdc{Approx} typeclass depends on the
\cdc{Data} typeclass, which is required for free variables.

The \cdc{Tick} datatype is a product type which uses an \cdc{Int} to represent
the computation cost associated with its value. It is essentially a writer
monad~\cite{moggi-monad,wadler-monad}. \cdc{List a} is the approximation type of
lists \cdc{[a]}. These types have all of the expected typeclass instances;
\eg~\cdc{Tick} is a \cdc{Monad}. These definitions are standard, and we omit them
for brevity.

\paragraph{Examples implemented.}
We manually apply the \transCname{} and \transDname{} on classical Haskell
functions and implement all translated functions in Curry. Examples we
implemented include appending lists, insertion sort, and Okasaki's banker's
queue~\cite{purely-functional}. We omit definitions of these translated
functions for space, but interested readers can view an insertion sort case
study in \cref{apx:case-study-insertion-sort}, and more in our publicly
available
artifact\footnote{https://github.com/heraplem/unifying-hindisght-and-foresight}.

\paragraph{Running computations.}
All the translated functions can be executed using the KiCS2 Curry compiler,
including all the logical clairvoyance functions. In addition, even though 
clairvoyance semantics returns a set of value-cost pairs due to nondeterminism,
we can use Curry's \emph{search tree}
functionality~\cite{DBLP:journals/jflp/BrasselHH04} to compute only the least
result, which is the true cost of lazy evaluation. In particular, the
\cdc{someValueWith} function defined in \cdc{Control.Search.SearchTree}
collapses a nondeterministic computation into a deterministic one according to a
given \emph{search strategy}, which tells Curry how to navigate a tree of
nondeterministic computations. In our implementation, we arrange our definitions
so that the less-defined result is always on the left branch of a search tree.
Thus, we can always find the least result via a depth-first search.

\paragraph{Guards vs.\ generators.}
In Curry, there are two ways of implementing the logical demand functions: 
guards and generators. Even though they are semantically equivalent, there
is a huge performance difference.

Na\"ively, we can implement \cdc{takeD} as follows:
\begin{lstlisting}[language=Curry]
takeD' :: Approx a => Int -> T (List a) -> List a -> Tick (T (List a))
takeD' xsT ysD |  xsTD <~ xsT
               && takeC n xsTD =:= Tick (ysD, c)
               =  Tick (xsTD, c)
  where xsTD, c free
\end{lstlisting}
In contrast to the definition in \cref{fig:takeD-curry}, we use the
\cdc{<~} operator in a guard condition in \cdc{takeD'} to assert that \cdc{xsTD}
is an approximation of \cdc{xsT}. In this case, Curry must ``guess'' a valid
input demand, performing poorly. On the other hand, our implementation in
\cref{fig:takeD-curry} uses a generator \cdc{approx} defined for the
\cdc{List} datatype, which is more efficient.

\paragraph{Performance.}

Although the \transDname{} is simpler than the original demand translation, the
question remains whether it is reasonably efficient, as it depends on the
\transCname{} and free variables. To evaluate\lai{Maybe choose another word,
  since 'evaluate' is a technical term} this, we ran \cdc{insertionSortD} on
lists of the form \cdc{[n, n-1 .. 1]} with sizes ranging from \(1\) to \(100\),
demanding the full list each time. We also ran \cdc{pushPopD}, the demand
translation of a function that pushes \(n\) elements onto a banker's
queue~\cite{purely-functional} and then pops them all. We show the result of our
performance evaluation in \cref{fig:insertionSortD_runtime}. All experiments
were performed on an AMD Ryzen 3900X running Linux 6.12.58 using the built-in
timing functionality of KiCS2 (version 3.5.0), taking the average of 10
executions.

  \centering
  \includegraphics[width=0.45\textwidth]{Figs/insertionSortD_runtime.png}
  \includegraphics[width=0.45\textwidth]{Figs/pushPopD_runtime.png}
  \caption{The runtime of
    \cdc{insertionSortD} and \cdc{pushPopD}.}\label{fig:insertionSortD_runtime}
\end{figure}

Asymptotically, \cdc{insertionSortD} appears to run in \(O(n^3)\) time: a cubic
interpolation estimates it well. This asymptotic bound is shared by the original
demand translation. However, the constants are much worse: \cdc{insertionSortD}
takes \(6.44\) seconds on a \(100\)-element list, while the original demand
translation version in Curry is fast enough that its runtime cannot be reliably
measured. \cdc{pushPopD}, meanwhile, takes \(12.30\) seconds to execute on
\(10\) elements.

This result is not surprising, as the original demand semantics is specialized
to computing minimal input demands, but the \transDname{} is built on a
general-purpose logic language. This experiment may reveal potential
optimization opportunities for Curry compilers.
