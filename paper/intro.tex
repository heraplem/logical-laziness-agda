\section{Introduction}\label{sec:intro}

Lazy evaluation is demand-driven, performing only those operations required to
compute a final result~\cite{launchbury1993}. This gives programmers the luxury
of writing highly compositional code that performs comparably to, or even better
than, code written in an eagerly-evaluated language~\cite{fp-matters}. Sadly, as
a ``side-effect,'' it presents challenges for performance analysis.

For example, consider the Haskell functions \cdh{take} and \cdh{(++)}, which
respectively take the length-\(n\) prefix of a list and concatenate two lists.
Suppose that we want to evaluate the following code:
\begin{lstlisting}[language=Haskell]
take 2 ([1,2,3] ++ [4,5]) 
\end{lstlisting}
In a lazy language like Haskell, such an expression is evaluated only insofar as
its result \emph{demands}. Suppose that we try to print just the first element
of the result: we run \cdh{take} and \cdh{(++)} once to obtain \cdh{1}. Now
suppose that we save the result in a variable and, in the future, try to print
the whole thing: at that point in time, we evaluate \cdh{take} and \cdh{(++)}
``one level deeper'' to obtain the second element, \cdh{2}, and \cdh{take} again
to obtain the end of the list, \cdh{[]}. These computations are evaluated
\emph{on demand} and \emph{out of order}, and they are \emph{interleaved}. Thus,
even in a pure language like Haskell, the performance characteristics of the
computation are inherently \emph{stateful}: the amount of work required to
evaluate a given expression depends on what has been evaluated previously.

How can we bring locality, purity, order, and compositionality to lazy
computation time costs when these properties are fundamentally missing? Some
recent work proposes that, instead of working with the stateful natural
semantics of lazy evaluation~\cite{launchbury1993}, we can use a simpler
\emph{alternative semantics} that is equivalent to lazy evaluation in terms of
computation cost. Here, we focus on two such semantics: clairvoyance
semantics~\cite{clairvoyant,forking-paths} and demand
semantics~\cite{bjerner1989,demand-semantics}.

\iffalse
  
Our goal is to develop a way to analyze the \emph{computation cost} of a lazy
functional program, so that the analysis is \emph{simple} and
\emph{compositional}. By simplicity, we mean that we should be able to use
simple tools like equational reasoning for simple properties about cost. By
compositionality, we mean that we can reason about each lazy function
individually, and compose properties about each function's cost when reasoning
about the whole program.



\paragraph{Other closely related approaches.}
Existing research that tackles this challenge can be divided into roughly three
different approaches. The first approach, represented by work on
Iris$^{\$}$~\cite{iris-credit,iris-thunk}, deals with mutable heaps directly,
but requires using special programming logics like the separation
logic~\cite{separation-logic}. The second approach, represented by
LiquidHaskell~\cite{liquidate,liquid-okasaki}, uses a graded monad proposed by
Danielsson~\cite{danielsson-08} to track computation cost. However, this
approach needs to deal with sharing manually. The third approach utilizes
alternative semantics that are equivalent to lazy evaluation in terms of
computation cost~\cite{bjerner1989,clairvoyant,forking-paths,demand-semantics}.
In contrast to the natural semantics of lazy evaluation~\cite{launchbury1993},
these semantics reify computation cost in pure and eager semantics, so we can
use them to reason about lazy computation cost without being concerned with
mutable heaps, sharing, or out-of-order executions.

\paragraph{Clairvoyance semantics.} Clairvoyance semantics, or clairvoyant
call-by-value, builds on the observation that, for analyzing computation costs,
it matters only \emph{whether} a computation cost is incurred, not
\emph{when}. Clairvoyance semantics evaluates terms eagerly, but when there is a
lazy operation, it makes a \emph{nondeterministic} choice to either evaluate the
computation or skip it.

To evaluate \cdh{take 2 ([1,2,3] ++ [4,5])} in clairvoyance semantics, we first
evaluate \cdh{[1,2,3] ++ [4,5]}. Each recursive function application is then
nondeterministically evaluated or skipped. The possible results of \cdh{[1,2,3]
  ++ [4,5]} are
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$},
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:2:$\bot$}, $\cdots$,
\cdh{[1,2,3,4,5]}, where $\bot$ represents a value whose evaluation is skipped.
Next, we run \cdh{take 2} over all the nondeterministic results of \cdh{[1,2,3]
  ++ [4,5]}. If a branch gets ``stuck,'' \eg~forcing the second element from
\lstinline[language=Haskell,breakatwhitespace,mathescape]{take 2 (1:$\bot$)}, we
discard it. In the end, one computation branch will have succeeded in the same
amount of time as a standard lazy evaluation.

Clairvoyance semantics can be used as a recipe for a mechanical translation from
a pure program to a program with reified computation costs~\cite{forking-paths}.
We show pseudo type signatures of translated \cdh{take} and \cdh{(++)} in
\cref{fig:hs-example-clairvoyance} as \cdh{takeC} and \cdh{appendC},
respectively. These translated functions use \emph{approximations} of lists,
denoted as \lstinline[language=Haskell,breakatwhitespace,mathescape]{[a]$^A$}.
They represent lists that are potentially ``less evaluated'', like
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}. We defer a
formal definition of approximations to \cref{subsec:values}. A natural
number~($\mathbb{N}$) in the result represents the associated computation cost.
Because the evaluation is nondeterministic, each translated function returns a
power set of result-cost pairs. We can use these translated functions to
formally reason about the computation cost of lazy programs, as illustrated by
Li \textit{et al.}~\cite{forking-paths}

One major drawback of this approach is that power sets in return types make
execution expensive. This makes it hard to use clairvoyance semantics in
testing.

\paragraph{Demand semantics.} Demand semantics builds on the observation that,
given a function's input and a demand on its output, we can evaluate the minimal
input demand required for such an output demand \emph{deterministically}.

In our example of \cdh{take 2 ([1,2,3] ++ [4,5])}, we first consider a demand on
the output,
\eg~\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}, where
$\bot$ represents parts of the list that are not evaluated. We then run the
\cdh{take} function ``backward'' to find that the minimal input demand required
for \cdh{take 2} is also
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}. We then run
the \cdh{(++)} function ``backward'' as well to find that the minimal input
demands required for the two input lists are
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$} and $\bot$,
respectively. Throughout this process, the associated computation cost is also
evaluated and carried. 

Demand semantics is also useful as a translation strategy~\cite{demand-semantics}. We show pseudo
type signatures of the translated functions \cdh{takeD} and \cdh{appendD} in
\cref{fig:hs-example-clairvoyance}. As in the clairvoyance translation, we use a natural number in
the result to represent computation cost. The demand translation also uses approximations like
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}, but it uses them to represent
demands.
% We do not need any power sets, as the demand semantics is deterministic.
For example, the input of \cdc{takeD} includes the input of \cdh{take}~(\cdh{Int} and
\cdh{[a]}), a demand on \cdh{take}'s
output~(\lstinline[language=Haskell,breakatwhitespace,mathescape]{[a]$^A$}). The return type of \cdc{takeD}  is the minimal demand on its
input~(\lstinline[language=Haskell,breakatwhitespace,mathescape]{[a]$^A$}) and
the cost~(\(\mathbb{N}\)). Note that the \cdh{Int} datatype is not lazy, so there is
no demand on it.

Because these demand functions are deterministic, computation costs are easy to
test. Unfortunately, the demand translation is more complicated than the
clairvoyance translation, because the ``backward'' direction of a function can
be complex. This complexity makes it challenging to develop tools to formally
reason about code under demand semantics.

\paragraph{Our contributions.}
It is unsatisfying that, although we have two semantics that model lazy
computation costs, they are very different and we have to choose between them
depending on what we need. In this paper, we propose a novel approach of
\emph{unifying} these two semantics using \emph{functional logic programming}.
In this new approach, we translate a lazy functional program to a functional
logic program that models clairvoyance semantics via a \emph{\transCname}. This
functional logic program can then be extended to obtain a new program that
encodes demand semantics via a \emph{\transDname} using a simpler wrapper. This
simple wrapper shows that there is a simple connection between clairvoyance
semantics and demand semantics. In other words, these two independently proposed
semantics are two sides of the same coin. We show this connection both in theory
and in practice.

    data T a = Undefined | Thunk a

    takeC :: Int -> T (List a) -> Tick (List a)
    takeC n xsT = do
      tick
      fcase n `compare` 0 of
        EQ -> return Nil
        GT -> do
          xs <- force xsT
          fcase xs of
            Nil -> return Nil
            x :~ xsT' -> (x:~) <$> thunk (takeC (n - 1) xsT')

    takeD :: Approx a => Int -> T (List a) -> List a -> Tick (T (List a))
    takeD n xsT ysD
        | takeC n xsTD =:= Tick (ysD, c)
        = Tick (xsTD, c)
      where xsTD = approx xsT
            c free
\end{lstlisting}

  implemented in Curry.}\label{fig:take-curry}

We show an example of translating the Haskell \cdh{take} function to
Curry~\cite{curry-lang} in \cref{fig:take-curry}. Function \cdc{takeC} is the
result of a \transCname{}, while \cdc{takeD} is the result of a \transDname{}.

The \cdc{takeC} function takes an \cdc{Int} and a \cdc{T (List a)}. The \cdc{T}
datatype represents a value that could be $\bot$~(represented by
\cdc{Undefined}). \cdc{List a} is the approximation of \cdh{[a]}. The function
returns a new \cdc{List a} inside a \cdc{Tick} monad, which encodes the
computation cost associated with the returned \cdc{List a}. The function works
similarly to \cdh{take} for the most part.\ly{TODO: explain \cdc{fcase} and
  \cdc{=:=}.} The key to implementing clairvoyance semantics is the recursive
call \cdc{thunk (takeC n' xsT')}, which unfolds to:
\begin{lstlisting}[language=Curry]
pure Undefined ? fmap Thunk (takeC n' xsT')
\end{lstlisting}
That is, we use Curry's nondeterministic choice operator \cdc{?} to either skip
the evaluation and return \cdc{Undefined} (\ie~$\bot$), or to evaluate the
recursive call and wrap the result inside a \cdc{Thunk} constructor.

The \cdc{takeD} function is implemented in terms of \cdc{takeC}. The core of
\cdc{takeD} is its guard condition: \cdc{takeC n xsTD =:= Tick (ysD, c)}, where
\cdc{n} and \cdc{ysD} are \cdc{takeD}'s arguments, and \cdc{xsTD} and \cdc{c}
are logic variables~(also known as free variables). In this way, \cdc{takeD}
computes the input \cdc{xsTD} and parts of the output \cdc{c} of \cdc{takeC},
given the rest of its output \cdc{ysD}. Put differently, \cdc{takeD} is an
\emph{inversion} of \cdc{takeC}. In addition, we require \cdc{xsTD} to be an
approximation of \cdc{xsT}, another argument of \cdc{takeD}, so that it either
is \cdc{xsT}, or is ``less evaluated'' than \cdc{xsT}.

More concretely, we make the following contributions:

\begin{itemize}
\item We propose and formalize two methods that translate
  functional programs to functional logic programs that reify lazy computation
  costs: a \transCname{} that encodes clairvoyance semantics, and a
  \transDname{} that wraps the \transCname{} and encodes demand
  semantics~(\cref{sec:translation}).
\item We formally prove that the \transCname{} and the \transDname{} are correct
  with respect to clairvoyance and demand semantics, respectively. All theorems
  and proofs are mechanized in the proof assistant
  Agda~\cite{DBLP:conf/tldi/Norell09}~(\cref{sec:equiv}).
  \item We conduct case studies by manually translating lazy Haskell programs,
        including insertion sort and Okasaki's banker's
        queue~\cite{purely-functional}, to Curry~\cite{curry-lang} based on our
        translation strategies. We evaluate the performance of translated code
        using the KiCS2 Curry compiler~\cite{kics2}, showing that \transDname{}
        trades off performance for simplicity, but the performance is usable for
        lazy cost analysis while allowing for simpler
        code~(\cref{sec:case-study}).
\end{itemize}
