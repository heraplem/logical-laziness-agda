In lazy evaluation, a computation is driven by its demands, performing only the
operations required to compute a final result~\cite{launchbury1993}. Lazy
evaluation enables functional programmers to write compositional code with
comparable or potentially better performance~\cite{fp-matters}. Unfortunately,
as a side effect, lazy evaluation also makes analyzing performance challenging.
% as the analyzer needs to reason about mutable heaps and cannot consider a
% function in isolation.

For concreteness, let's consider the Haskell functions \cdh{take} and \cdh{(++)}
defined in \cref{fig:hs-example-original}. Suppose that we are going to evaluate
the following piece of code:
\begin{lstlisting}[language=Haskell]
  take 2 ([1,2,3] ++ [4,5]) 
\end{lstlisting}
This program only evaluates when its result is demanded, \eg~when we print the
result. When there is a demand, say on the first element, we will run \cdh{take}
and \cdh{append} once to obtain the first element \cdh{1}. However, suppose that
there is a point in the future, we demand the entire result list. We will then
evaluate \cdh{take} and \cdh{append} ``one level deeper'' to obtain the second
element \cdh{2}, and \cdh{take} again to obtain the end of the result list:
\cdh{[]}. This example shows that computations in a lazy program are evaluated
on demand, out of order, and interleaved with other computations. These
characteristics make analyzing the ``performance'' of a lazy functional program
challenging.

How can we bring simplicity, order, and compositionality to lazy computation
cost, where these properties are fundamentally absent in the semantics? Some
recent works proposed that, instead of dealing with the stateful natural
semantics of lazy evaluation~\cite{launchbury1993}, we can utilize simpler
\emph{alternative semantics} that are equivalent to lazy evaluation in terms of
computation cost. Two notable semantics are the clairvoyance
semantics~\cite{clairvoyant,forking-paths} and the demand
semantics~\cite{bjerner1989,demand-semantics}.

\iffalse
  
Our goal is to develop a way to analyze the \emph{computation cost} of a lazy
functional program, so that the analysis is \emph{simple} and
\emph{compositional}. By simplicity, we mean that we should be able to use
simple tools like equational reasoning for simple properties about cost. By
compositionality, we mean that we can reason about each lazy function
individually, and compose properties about each function's cost when reaosning
about the whole program.



\paragraph{Other closely related approaches.}
Existing research that tackles this challenge can be divided into roughly three
different approaches. The first approach, represented by work on
Iris$^{\$}$~\cite{iris-credit,iris-thunk}, deals with mutable heaps directly,
but requires using special programming logics like the separation
logic~\cite{separation-logic}. The second approach, represented by
LiquidHaskell~\cite{liquidate,liquid-okasaki}, uses a graded monad proposed by
Danielsson~\cite{danielsson-08} to track computation cost. However, this
approach needs to deal with sharing manually. The third approach utilizes
alternative semantics that are equivalent to lazy evaluation in terms of
computation cost~\cite{bjerner1989,clairvoyant,forking-paths,demand-semantics}.
In contrast to the natural semantics of lazy evaluation~\cite{launchbury1993},
these semantics reify computation cost in pure and eager semantics, so we can
use them to reason about lazy computation cost without being concerned with
mutable heaps, sharing, or our-of-order executions.

\paragraph{The clairvoyance semantics.} The clairvoyance semantics, or the
clairvoyance call-by-value semantics, builds on the observation that, for the
sake of analyzing computation cost, it only matters \emph{if} a computation cost
is incurred, not \emph{when}. Therefore, the clairvoyance semantics evaluates
terms eagerly, but every time it runs into a lazy operation, it makes a
\emph{nondeterministic} choice of evaluating a computation or skipping it.

In our example of \cdh{take 2 ([1,2,3] ++ [4,5])}, we first evaluate
\cdh{[1,2,3] ++ [4,5]}, but every time there is a functional application, we
nondetermistically evaluate it or skip it, as illustrated in
\cref{fig:forking-paths}. Afterwards, we run \cdh{take 2} in the same way over
all the nondeterministic results of \cdh{[1,2,3] ++ [4,5]}. When it is not
possible to evaluate, \eg~we want the second element from
\lstinline[language=Haskell,breakatwhitespace,mathescape]{take 2 (1:$\bot$)}, we
discard the current nondeterministic branch. Eventually, one of the
nondeterministic results gives the cost of lazy evaluation.

We can use the clairvoyance semantics as a recipe for a mechanical translation
from a pure program to a program where computation cost is
reified~\cite{forking-paths}. We show the type signatures of the translated
\cdh{take} and \cdh{(++)} in \cref{fig:hs-example-clairvoyance}, where we called
them \cdh{takeC} and \cdh{appendC}, respectively. These translated functions are
based on \emph{approximations} of lists, denoted as
\lstinline[language=Haskell,breakatwhitespace,mathescape]{[a]$^A$}. They
represent lists that are potentially ``less evaluated''.\ly{Mention that we will
  talk about the formal definition in later sections.} We use a natural
number~($\mathbb{N}$) in the returned result to represent the associated
computation cost. Each translated function returns a power set of result and
cost pairs, due to nondeterministic evaluation.

We can use these translated functions to formally reason about computation cost
of lazy programs. However, a major drawback of these functions is that the power
sets in returned types make execution challenging. This makes it hard to apply
the clairvoyance semantics to testing.

\paragraph{The demand semantics.} The demand semantics builds on the observation
that, given the input and a demand on the output, we can compute the minimal
demand on the input required for such output demand. This process is
\emph{deterministic}.

In our example of \cdh{take 2 ([1,2,3] ++ [4,5])}, we first consider a demand on
the output,
\eg~\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}, where
$\bot$ represents parts of the list that we do not care about. We then run the
\cdh{take} function ``backward'' to find that the minimal input demand required
for \cdh{take 2} is also
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}. We then run
\cdh{(++)} function ``backward'' as well to find that the minimal input demand
required for the two input lists are
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$} and $\bot$,
respectively. Along the way of computing the minimal input demand, the demand
semantics also computes the computation cost associated with it.

We can also use the demand semantics as a translation
strategy~\cite{demand-semantics}. We show the type signatures of translated
functions, \cdh{takeD} and \cdh{appendD}, in \cref{fig:hs-example-demand}.
Similar to the clairvoyance translation, we use natural numbers in the result to
represent computation costs. The demand translation also uses approximations,
but it uses them to represent demands. We no longer need any power sets in these
type signatures, as the demand semantics is deterministic.

We can test computation costs using these translated functions, because they are
determisnitic. Unfortunately, the demand translation is much more complicated
than the clairvoyance translation, this makes it more challenging for developing
tools for this translation or formally reasoning about translated code.

\paragraph{Two sides of the same coin.}
It is unsatisfying that even though we have two semantics that model lazy
computation costs, they are very different and we have to choose depending on
what we need.

In this paper, we propose that \emph{functional logic programming} can help
unify these two semantics. Indeed, nondeterministic choices in functional logic
programming are natural fit for modeling the clairvoyance semantics. On the
other hand, the demand semantics can be considered a variant of function
inversion, so it can be modeled using free variables (also known as logical
variables). In particular, we show that both semantics can be represented by one
simple, executable functional logic program, revealing that they are in fact two
sides of the same coin. In this paper, we demonstrate this connection both in
theory and in practice.

We make the following contributions:

\begin{itemize}
  \item We propose and formalize a mechanical way of translating functional
        programs to functional logic programs that reify lazy computation costs:
        a \transCname{} that encodes the clairvoyance semantics, and a
        \transDname{} that is a thin wrapper of the \transCname{} and encodes
        the demand semantics~(\cref{sec:translation}).
  \item We formally prove that both \transCname{} and \transDname{} are correct
        with respect the clairvoyance semantics and the demand semnatics,
        respectively. All theorems and proofs are mechanized in
        Agda~(\cref{sec:equiv}).
  \item We conduct several case studies by manually translating some lazy
        Haskell programs, including insertion sorts, to Curry~\cite{curry-lang}
        based on our translation strategy. We also evaluate the performance of
        translated code based on the KiCS2 Curry
        compiler~\cite{DBLP:conf/wflp/BrasselHPR11}, which shows that acceptable
        performance although the translated code is much simpler and reveals
        potential optimization opportunities for Curry
        compilers~(\cref{sec:case-study}).
\end{itemize}
