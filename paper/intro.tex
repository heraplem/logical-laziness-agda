Let's consider the Haskell functions \cdh{take} and \cdh{(++)} as a concrete example,
defined in \cref{fig:hs-example-original}. Suppose that we are going to evaluate
the following piece of code:
\begin{lstlisting}[language=Haskell]
  take 2 ([1,2,3] ++ [4,5]) 
\end{lstlisting}
This program only evaluates when its result is demanded, \eg~when we print the
result. When there is a demand, say on the first element, we will run \cdh{take}
and \cdh{(++)} once to obtain the first element, \cdh{1}. However, suppose that, in the future, we demand the entire list. We will then
evaluate \cdh{take} and \cdh{(++)} ``one level deeper'' to obtain the second
element, \cdh{2}, and \cdh{take} again to obtain the end of the list:
\cdh{[]}. These computations (and those in other lazy programs) are evaluated \emph{on demand}, \emph{out of order}, and are
\emph{interleaved}. Common cost models often cannot accommodate some or all of these properties of laziness, leading to the aforementioned difficulties in performance analysis.

How can we bring simplicity, order, and compositionality to lazy computation costs when these properties are fundamentally absent in the semantics? Some
recent works propose that, instead of handling the stateful natural
semantics of lazy evaluation~\cite{launchbury1993}, we can utilize simpler
\emph{alternative semantics} that are cost-equivalent to lazy evaluation. Two such semantics, which are the focus of our work, are clairvoyance
semantics~\cite{clairvoyant,forking-paths} and demand
semantics~\cite{bjerner1989,demand-semantics}.

\iffalse
  
Our goal is to develop a way to analyze the \emph{computation cost} of a lazy
functional program, so that the analysis is \emph{simple} and
\emph{compositional}. By simplicity, we mean that we should be able to use
simple tools like equational reasoning for simple properties about cost. By
compositionality, we mean that we can reason about each lazy function
individually, and compose properties about each function's cost when reaosning
about the whole program.



\paragraph{Other closely related approaches.}
Existing research that tackles this challenge can be divided into roughly three
different approaches. The first approach, represented by work on
Iris$^{\$}$~\cite{iris-credit,iris-thunk}, deals with mutable heaps directly,
but requires using special programming logics like the separation
logic~\cite{separation-logic}. The second approach, represented by
LiquidHaskell~\cite{liquidate,liquid-okasaki}, uses a graded monad proposed by
Danielsson~\cite{danielsson-08} to track computation cost. However, this
approach needs to deal with sharing manually. The third approach utilizes
alternative semantics that are equivalent to lazy evaluation in terms of
computation cost~\cite{bjerner1989,clairvoyant,forking-paths,demand-semantics}.
In contrast to the natural semantics of lazy evaluation~\cite{launchbury1993},
these semantics reify computation cost in pure and eager semantics, so we can
use them to reason about lazy computation cost without being concerned with
mutable heaps, sharing, or our-of-order executions.

\paragraph{Clairvoyance semantics.} Clairvoyance semantics, or
``clairvoyant call-by-value semantics,'' builds on the observation that, for the
sake of cost analysis, it only matters \emph{if} a computation cost
is incurred, not \emph{when}. Therefore, clairvoyance semantics evaluates
terms eagerly, but every time it encounters a lazy operation, it makes a
\emph{nondeterministic} choice of evaluating the computation or skipping it.

When we apply clairvoyance semantics to \cdh{take 2 ([1,2,3] ++ [4,5])}, we
first evaluate
\cdh{[1,2,3] ++ [4,5]}. Each function
application is either nondetermistically evaluated or skipped, as illustrated in
\cref{fig:forking-paths}. The results of \cdh{[1,2,3] ++ [4,5]} include
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$},
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:2:$\bot$}, $\cdots$,
and \cdh{[1,2,3,4,5]}, where $\bot$ represents a value whose evaluation is
skipped. Afterwards, we run \cdh{take 2} in the same way over all the
nondeterministic results of \cdh{[1,2,3] ++ [4,5]}. When evaluation is impossible, \eg~forcing the second element from
\lstinline[language=Haskell,breakatwhitespace,mathescape]{take 2 (1:$\bot$)}, we
discard the current nondeterministic branch. Eventually, one of the
nondeterministic results gives the cost of lazy evaluation.

We can use clairvoyance semantics as a recipe for a mechanical translation
from a pure program to a program where computation cost is
reified~\cite{forking-paths}. We show type signatures of the translated
\cdh{take} and \cdh{(++)} in \cref{fig:hs-example-clairvoyance} as \cdh{takeC} and \cdh{appendC}, respectively. These translated functions are
based on \emph{approximations} of lists, denoted as
\lstinline[language=Haskell,breakatwhitespace,mathescape]{[a]$^A$}. They
represent lists that are potentially ``less evaluated'', like  \lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}. A
natural number~($\mathbb{N}$) in the result represents the associated
computation cost. Each translated function returns a power set of result and
cost pairs due to nondeterministic evaluation.

We can use these translated functions to formally reason about the computation cost
of lazy programs. One major drawback of this approach is that power
sets in returned types make execution expensive. This makes it hard to apply
the clairvoyance semantics to testing.

\paragraph{Demand semantics.} Demand semantics builds on the observation
that, given an input and a demand on a function's output, we can compute the minimal
input demand required for such an output demand
\emph{deterministically}.

In our example of \cdh{take 2 ([1,2,3] ++ [4,5])}, we first consider a demand on
the output,
\eg~\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}, where
$\bot$ represents parts of the list that are not evaluated. We then run the
\cdh{take} function ``backward'' to find that the minimal input demand required
for \cdh{take 2} is also
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}. We then run
\cdh{(++)} function ``backward'' as well to find that the minimal input demands
required for the two input lists are
\lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$} and $\bot$,
respectively. Throughout this process, the associated computation cost is also computed and carried forward.

We can also use the demand semantics as a translation
strategy~\cite{demand-semantics}. We show type signatures of translated
functions, \cdh{takeD} and \cdh{appendD}, in \cref{fig:hs-example-demand}.
Similar to the clairvoyance translation, we use natural numbers in the result to
represent computation costs. The demand translation also uses approximations
like \lstinline[language=Haskell,breakatwhitespace,mathescape]{1:$\bot$}, but it
uses them to represent demands.
% We do not need any power sets, as the demand semantics is deterministic.

Because these functions are deterministic, computation costs are easy to test. Unfortunately, the demand translation is much more
complicated than the clairvoyance translation, which makes it more challenging
to develop tools for or formally reason about code under demand semantics.

\paragraph{Two sides of the same coin.}
We propose a novel approach of \emph{unifying} these two dissimilar but provably cost-equivalent
semantics using \emph{functional logic programming}. In this new approach, we
translate a lazy functional program to a functional logic program that
models clairvoyance semantics via a \emph{\transCname}. This
functional logic program can be extended to obtain a new program that
encodes demand semantics via a \emph{\transDname}.

We show an example of translating the Haskell \cdh{take} function to Curry~\cite{curry-lang} in \cref{fig:take-curry}. \Cref{fig:takeC-curry}
shows the result of a \transCname, the definition of \cdc{takeC} in Curry.
\Cref{fig:takeD-curry} shows the the result of a \transDname, \cdc{takeD}, which
is a simple wrapper of \cdc{takeC}. Both \cdc{takeC} and \cdc{takeD} rely on
some common definitions shown in \cref{fig:curry-thunk-func}.

The \cdc{takeC} function takes an \cdc{Int}, and a \cdc{T (List a)} that represents
a list with $\bot$s as arguments. It returns a new list \lai{What type?} with $\bot$s in the
\cdc{Tick} monad, which encodes computation cost. Most of the function works
similarly to \cdh{take}. The key for implementing clairvoyance semantics is
the recursive call \cdc{thunk (takeC n' xsT')}, which unfolds to:
\begin{lstlisting}[language=Curry]
pure Undefined ? fmap Thunk (takeC n' xsT') 
\end{lstlisting}
That is, every time we make a recursive call, we use Curry's nondeterministic
choice operator \cdc{?} to either skip the evaluation by returning
\cdc{Undefined}, or evaluate the recursive call and wrap the result inside the
\cdc{Thunk} constructor.

The \cdc{takeD} function, on the other hand, relies on \cdc{takeC}. The core of
\cdc{takeD} is in its guard expression: \cdc{takeC n xsTD =:= Tick (ysD, c)},
where \cdc{n} and \cdc{ysD} are \cdc{takeD}'s arguments, and \cdc{xsTD} and \cdc{c}
are free variables~(also known as logical variables). In this way, \cdc{takeD}
computes the input \cdc{xsTD} and parts of the output \cdc{c} of \cdc{takeC},
given the rest of its output \cdc{ysD}. Put differently, \cdc{takeD} is a weaker
form of a \emph{function inversion} of \cdc{takeC}. In addition, we require that
\cdc{xsTD} to be an approximation of \cdc{xsT}, another argument of \cdc{takeD},
so that it is either \cdc{xsT} or ``less evaluated'' than \cdc{xsT}.

\paragraph{Our contributions.}
By utilizing functional logic programming, we show that both the clairvoyance
semantics and the demand semantics can be represented by two ways of evaluating
one functional logic program, revealing that they are two sides of the same
coin. In this paper, we show this connection both in theory and in practice.

In addition, our result shows a simple way of executing clairvoyance semantics
by utilizing functional logic language compilers like the KiCS2 Curry compiler,
which supports flexible search strategies and features to encapsulate
nondeterministic computations~\cite{kics2}. Our result also shows a simpler way
of encoding the demand semantics by utilizing free variables in logic languages.
Our evaluation shows that this simpler approach achieves acceptable performance.

More concretely, we make the following contributions:

\begin{itemize}
  \item We propose and formalize a mechanical way of translating functional
        programs to functional logic programs that reify lazy computation costs:
        a \transCname{} that encodes the clairvoyance semantics, and a
        \transDname{} that is a thin wrapper of the \transCname{} and encodes
        the demand semantics~(\cref{sec:translation}).
  \item We formally prove that both \transCname{} and \transDname{} are correct
        with respect the clairvoyance semantics and the demand semnatics,
        respectively. All theorems and proofs are mechanized in
        Agda~(\cref{sec:equiv}).
  \item We conduct several case studies by manually translating some lazy
        Haskell programs, including insertion sorts, to Curry~\cite{curry-lang}
        based on our translation strategy. We also evaluate the performance of
        translated code based on the KiCS2 Curry compiler~\cite{kics2}, which
        shows that acceptable performance although the translated code is much
        simpler and reveals potential optimization opportunities for Curry
        compilers~(\cref{sec:case-study}).
\end{itemize}

In addition, we discuss related work in \cref{sec:related-work} and conclude
this paper in \cref{sec:conclusion}.
