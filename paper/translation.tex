\subsection{The Base Language \(\LB\)}\label{subsec:base-lang}

We show the syntax of the base language \(\LB\) in \cref{fig:syntax-base}.
Language \(\LB\) is a simply typed calculus with booleans, lists, and lazy
thunks (\ie~suspended computations). Its terms include variables,
\(\tletZ\)-bindings, conditionals, and recursion based on \(\tfoldrZ\). In
addition, it contains \( \tlazyZ \) and \( \tforceZ \) operators, which wrap a
computation in a lazy thunk and force a computation from a thunk,
respectively.
% The \(\TThunkZ\) type represents thunks in lazy evaluation.
Finally, the \( \ttickZ \) operator incurs one unit of computation cost. These
explicit operators decouple our analysis from any particular evaluation model.

\(\LB\) does not have higher-order functions or general recursion because
demand semantics does not support these
features~\cite{bjerner1989,demand-semantics}. The lack of higher-order functions
does not fundamentally limit \(\LB\)'s expressivity, as any higher-order
program can be
defunctionalized~\cite{DBLP:conf/acm/Reynolds72,DBLP:conf/ppdp/DanvyN01} to an
equivalent first-order program.\nc{The ``story of your function's life'' paper
  says that the language does not support higher-order functions; but, really,
  it doesn't even support \emph{first-class} functions. So is it even worth
  mentioning defunctionalization here? I'm pretty sure this still isn't a
  fundamental limit on expressivity, though.} The lack of general recursion
\emph{is} a fundamental limitation on expressivity, but it is not a problem for
cost analysis. We can simulate general recursion without any change in
asymptotic complexity by providing a ``fuel'' parameter that decreases on every
recursive call.

Most of the typing rules for \(\LB\) are standard, so we omit them. We show the
typing rules for thunks and computation costs in \cref{fig:typing-base}.
Notably, lists are lazy: the cons of lists \(\tcons{t_1}{t_2}\) takes a term
\(t_1\) of type \(A\) and a term \(t_2\) of type \(\TThunk{(\TList{A})}\), so
the tail of a list must always be wrapped in a \(\TThunkZ\). Similarly, the
``function'' argument to \(\tfoldrZ\) always requires that its second parameter
be wrapped in a \(\TThunkZ\).

We can give language \(\LB\) a denotational semantics \(\EE{t}{\gamma}\) for any
term \(t\) in an environment \(\gamma\) by simply ignoring all operations
related to lazy evaluation and computation costs:
\[
  \EE{\tlazy{t}}{\gamma} = \EE{\tforce{t}}{\gamma} = \EE{\ttick{t}}{\gamma} = \EE{t}{\gamma} .
\]
We do not need to model the natural semantics of \(\LB\) because prior work has
established computation cost equivalence between natural semantics and
clairvoyance semantics~\cite{clairvoyant}, and between clairvoyance semantics
and demand semantics~\cite{demand-semantics}.

\subsection{The Logic Language \(\LL\)}\label{subsec:logic-lang}

We show the syntax of language \(\LL\) in \cref{fig:syntax-logic}. Compared with \(\LB\),
\(\LL\) has more types: a unit type \(\TUnit\), natural numbers
\(\TNat\), and product types \(\TProd{A}{B}\). \ifextended We need the natural
  number type to model computation costs, and we need product types to return
  computation results along with costs. Since we are going to model demand
  semantics, we also need products to model evaluation contexts, and we need the
  unit type to model \emph{empty} contexts. \else We need natural numbers and
  products to represent computation costs associated with values, and we need
  products and the unit type to represent environments. Note that the types of
  \(\LL\) are a superset of the types of \(\LB\). As a consequence, any valid
  typing context for \(\LB\) is also a valid typing context for \(\LL\). \fi

In addition, we introduce two constructors for the \(\TThunkZ\) type:
\(\tresultZ\) for the result of an expression that has been evaluated, and
\(\tundefined\) for the result of an expression\lai{expression or evaluation?} that has been skipped~(\ie~the
$\bot$ we used in \cref{sec:intro}). In the \transCname{}, these two
constructors indicate whether a computation is evaluated or not. In the
\transDname, they indicate whether a computation is demanded or not.

\(\LL\) has introduction and elimination forms for all of the new types. We have
no need for arbitrary functions on natural numbers, so we include only literals
and addition. \(\LL\) also has constructs for logic programming: free
terms~(\(\tfreeZ\)), nondeterministic choice~(\(\tchooseZ\)), and
failure~(\(\tfail\)). Free terms, which may evaluate to any value of a specified
type, can be thought of as ``anonymous logic variables'': variables bound to
free terms are equivalent to logic variables. Finally, we have a relational
operator \(\tleZ\), which indicates whether its left-hand operand is less
defined than its right-hand operand (as defined in
\cref{subsec:values}).

\paragraph{Derived terms in \(\LL\).}
We use \(\LL\) to implement functional logic programs that ``carry'' a
computation result and its associated computation cost. To encapsulate
operations related to computation costs, we define some derived term constructs
in \(\LL\) in \cref{fig:logic-derived}. We use \treturn{t} to lift \(t\) to a
computation that costs \(0\). We use \tdo{x}{t_1}{t_2} to chain computations
\(t_1\) and \(t_2\) while accumulating their costs. We use
\tfoldM{x_1}{x_2}{t_1}{t_2}{t_3} to chain a list of computations, accumulating
all of their costs. The \tfoldMZ{} operation employs an auxiliary construct
\ttransposeZ, which converts terms of type \(\TThunk{(\TM{A})}\) to terms of
type \(\TM{(\TThunk{A})}\). In addition, we define \tassertZ{}, which ensures
that a given condition holds, causing the computation to fail if it does not.

We show all the typing rules related to these derived terms in
\cref{fig:logic-derived} as well. Readers who are familiar with monads might
recognize \texttt{M} as a writer monad~\cite{moggi-monad,wadler-monad}.

\subsection{Exact Values and Approximations}\label{subsec:values}

Each type \(A\) comes equipped with a set \(\Eval{A}\) of \emph{exact values}
and a set \(\Approx{A}\) of \emph{approximation values}, defined in
\cref{fig:exact-approx}. The exact values are standard; \eg\ the exact values of
\(\TNat\) are natural numbers, and the exact values of \(\TList{A}\) are finite
sequences with elements drawn from the exact values of \(A\). The approximation
values are similar to the exact values, except some parts might be
``discarded''~(represented by \(\sundefined\)). They represent ``smaller''
values where certain computations are unneeded; \ie~they are approximations of
the exact values.

\begin{figure}[t]
\begin{center}
  \begin{align*}
    \Eval{\TThunk{A}} &= \Eval{A} \\
    \Eval{\TUnit} &= \SUnit \\
    \Eval{\TBool} &= \SBool \\
    \Eval{\TProd{A}{B}} &= \Eval{A} \times \Eval{B} \\
    \Eval{\TNat} &= \N \\
    \Eval{\TList{A}} &= \braces{\snil} \cup \setbuilder{\scons{v_1}{v_2}}{v_1 \in \Eval{A}, v_2 \in \Eval{\TList{A}}} \\ \\
    \Approx{\TLazy{A}} &= \set{\sundefined} \cup \setbuilder{\sthunk{v}}{v \in \Approx{A}} \\
    \Approx{\TProd{A}{B}} &= \Approx{A} \times \Approx{B} \\
    \Approx{\TList{A}} &= \set{\snil} \cup \setbuilder{\scons{v_1}{v_2}}{v_1 \in \Approx{A}, v_2 \in \Approx{\TThunk{(\TList{A})}}}
  \end{align*}
\end{center}
\caption{Exact and approximation values. \(\Approx{A} = \Eval{A}\)
  wherever \(\Approx{A}\) is not otherwise specified.}\label{fig:exact-approx}
\end{figure}

We extend \(\Eval{\cdot}\) and \(\Approx{\cdot}\) to typing contexts. If
\(\Gamma = x_1 : A_1, \ldots, x_n : A_n \) is a typing context, then
\(\Eval{\Gamma}\) is the set of environments of shape \(\Gamma\) that bind
variables to exact values:
\[
  \Eval{\Gamma} = \setbuilder{x_1 \mapsto e_1, \ldots, x_n \mapsto e_n}{e_1 \in \Eval{A_1}, \ldots, e_n \in \Eval{A_n}}.
\]
\(\Approx{\Gamma}\) is defined similarly.

Exact values and approximations are connected by the relation \(\approxofZ\)
(\cref{fig:approx}). Intuitively, \(\approxof{a}{e}\), pronounced ``\(a\)
approximates \(e\)'', if \(a\) has the same shape as \(e\), but with some parts
possibly replaced by \(\sundefined\). If \(e \in \Eval{A}\), we write
\(\Approx{A}_{\approxof{\relax}{e}}\) to denote the set of values in
\(\Approx{A}\) that approximate \(e\):
\[
  \Approx{A}_{\approxof{\relax}{e}} = \setbuilder{a \in \Approx{A}}{\approxof{a}{e}} .
\]
Similarly, if \(\gamma \in \Eval{\Gamma}\), we write
\(\Approx{\Gamma}_{\approxof{\relax}{\gamma}}\) to denote the set of
environments that elementwise approximate \(\gamma\).

Approximations come with a \emph{definedness} relation (\cref{fig:definedness}).
It is conceptually similar to the approximation relation: \(a \le a'\),
pronounced ``\(a\) is less defined than \(a'\)'', if \(a\) has the same shape as
\(a'\) with some parts replaced by \(\sundefined\). This relation is a partial order on approximations.

We also extend \(\le\) to environments. Given \(\gamma \in \Eval{\Gamma}\) and
\(\gamma^A_1, \gamma^A_2 \prec \gamma\), we say that
\(\gamma^A_1 \le \gamma^A_2\) if each value in \(\gamma^A_1\) is less defined
than the corresponding value in \(\gamma^A_2\). This relation inherits all of
the algebraic properties of \(\le\) on environments; in particular, it is a
partial order.

\subsection{\TransCname{} and \TransDname{}}\label{subsec:clairvoyance-translation}\label{subsec:demand-translation}

We define the \transCname{} \(\transC{\cdot}\) in \cref{fig:transC}. The
\transCname{} translates terms in \(\LB\) to terms in \(\LL\) that simulate
clairvoyance semantics. Values and variables are translated using \treturnZ.
Variable bindings~(\tletZ) and conditionals~(\tifZ) are translated via
sequencing (\tdo{\cdot}{\cdot}{\cdot}). Folds (\tfoldrZ{}) are translated to the
derived term construct \tfoldMZ. Readers familiar with monads might recognize
that this is essentially a monadic
translation~\cite{moggi-monad,malias,wadler-monad} with adaptations for the
\TLazyZ{} type~\cite{forking-paths}.

The most important cases of the translation are those for \(\tlazyZ\) and
\(\tforceZ\). When the original term is \(\tlazy{t}\), we use the
nondeterministic choice operator \texttt{?} to either skip the inner term
(\(\treturn{\tundefined}\)) or evaluate the inner term and wrap the result
inside a \tresultZ. When the original term is \(\tforce{t}\), we first evaluate
\(t\) and then pattern match on the result \(y_1\): if \(y_1\) evaluates to
\(\tresult{y_2}\), then we return \(y_2\); otherwise, we \tfail. Note that
\tfail{} only terminates the current computation branch, so any branches where
\(y_1\) evaluates to a \tresultZ{} will continue. To \ttickZ{} a computation, we
simply run it and increment its accumulated cost by \(1\).

We also define the \transDname{} \(\transD{t}{\Gamma}\) from \(\LB\) to \(\LL\)
in \cref{fig:demand-translation}. Unlike the \transCname{}, the \transDname{}
also takes as a parameter a typing context \(\Gamma\) such that
\(\TB{\Gamma}{t}{A}\) (for some type \(A\)). This is because the \transDname{}
must know the names and types of \(t\)'s free variables. This treatment is the
same as the demand translation of Xia \textit{et
  al.}~\cite{demand-semantics}. As output, \(\transD{t}{\Gamma}\) produces a
term in \(\LB\) that has all the same free variables as \(t\), plus an
additional free variable \(x\), which represents a demand on the output of
\(t\).
% (We make this precise in \cref{thm:transD-type}.)

Intuitively, \(\transD{t}{\Gamma}\) operates as follows.
\begin{itemize}
\item For each variable \(x_i : A_i\) free in \(\Gamma\), introduce a new logic
  variable \(x_i' : A\) such that \(x_i' \le x_i\).
\item Pass \(t\) through the \transCname\ and execute it, but with each \(x_i\)
  replaced by the corresponding logiv variable \(x'_i\). This yields a
  result-cost pair \(u\).
\item Constrain the result \(\tfst{u}\) to be equal to the input \(x\).
\item Return a tuple containing the values of all the new logic variables, along
  with the cost \(\tsnd{u}\).
\end{itemize}
This is a special case of the common logic programming idiom of function
inversion: \(\transD{t}{\Gamma}\) computes the inverse of \(\transC{t}\),
constraining the result to be an approximation of the inputs to \(\transC{t}\).

We prove that \transCname{} and \transDname{} preserve well-typedness of the
original term in \(\LB\):
\begin{theorem}
  If \( \TB{\Gamma}{t}{A} \), then \( \TL{\Gamma}{\transC{t}}{\TM{A}} \).
\end{theorem}

\begin{theorem}\label{thm:transD-type}
  If \( \TB{\Gamma}{t}{A} \), then \( \TL{\Gamma, x : A}{\transD{t}{\Gamma}}{\TM{\verts{\Gamma}}} \).
\end{theorem}
The operation \( \verts{\cdot} \) turns typing contexts into product types. Both
theorems are formalized and proven in Agda, which is included in our
publicly-available artifact.
