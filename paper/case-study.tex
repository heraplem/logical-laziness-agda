\section{Case Studies}\label{sec:case-study}

In this section, we briefly outline and evaluate an implementation of our
translation in the functional logic programming language Curry. Note that all of
our definitions have been tested specifically with the KiCS2 Curry
compiler~\cite{DBLP:conf/wflp/BrasselHPR11}.

\subsection{Foundations}

We begin by building a framework for representing lazy computations.
\begin{lstlisting}[language=Curry]
data T a = Undefined | Thunk

thunk :: Applicative f => f a -> f (T a)
thunk f = pure Undefined ? fmap Thunk f

forcing :: T a -> (a -> b) -> b
forcing (Thunk v) f = f v

with :: Applicative f => T a -> (a -> f b) -> f (T b)
with t k = thunk (forcing t k)
\end{lstlisting}
\texttt{T} is the type of computations that may or may not occur. The
\texttt{thunk} combinator nondeterministically to either run an effectful
computation or discard it, which (in clairvoyance semantics) amounts to making
the computation lazy. The \texttt{forcing} combinator applies a function to a
lazily-computed value, provided that is has in fact been computed. The
\texttt{with} combinator pushes an effectful computation through a \texttt{T},
yielding \texttt{Undefined} if no value is present.

\begin{lstlisting}[language=Curry]
infix 4 <~
class Data a => Approx a where
  (<~) :: a -> a -> Bool

  approx :: a -> a
  approx x | y <~ x = y
    where y free

instance Approx a => Approx (T a) where
  Undefined <~ _         = True
  Thunk _   <~ Undefined = False
  Thunk x   <~ Thunk y   = x <~ y
\end{lstlisting}
\texttt{Approx} is the class of approximation types. The operator \texttt{<\char`\~} indicates whether its left-hand operand approximates its-hand operand. The function \texttt{approx} nondeterministically returns some value that approximates its argument. \texttt{approx} has a default implementation in terms of \texttt{free}, but specialized implementations can be much faster. We need the \texttt{Data} constraint in order to generate free variables.

\begin{lstlisting}[language=Curry]
newtype Tick a = Tick { runTick :: (a, Int) }
\end{lstlisting}
The \texttt{Tick} type is essentially a writer monad over the additive monoid of natural numbers.

\begin{lstlisting}[language=Curry]
infixr 5 :~
data List a = Nil | (:~) a (T (List a))

fromList :: [a] -> List a
fromList = foldr (\x xs -> x :~ Thunk xs) Nil
\end{lstlisting}
\texttt{List} is the type of lists whose tails may be \texttt{Undefined}; \ie\ they are computed lazily.

The foregoing types have all of the expected typeclass instances; \eg \texttt{Monad} for \texttt{Tick}. The definitions are standard; we omit them for brevity.

\subsection{Running computations}

Now we can start defining some functions.
\begin{lstlisting}[language=Curry]
takeC :: Int -> T (List a) -> Tick (List a)
takeC n xsT = do
  tick
  fcase n `compare` 0 of
    EQ -> return Nil
    GT -> do
      let n' = n - 1
      xs <- force xsT
      fcase xs of
        Nil -> return Nil
        x :~ xsT' -> do
          ysT' <- thunk (takeC n' xsT')
          return (x :~ ysT')
\end{lstlisting}
\texttt{takeC} is the clairvoyance translation of the standard \texttt{take} function, which computes the length-\(n\) prefix of a list. The list argument is wrapped in a \texttt{T} because it need not be demanded at all if \(n = 0\). The case analysis construct \texttt{case} residuates on free variables, so we instead use Curry's ``flexible'' case analysis construct \texttt{fcase}, which evaluates by narrowing.

Finally, following the construction outlined in earlier sections, we can implement the demand function \texttt{takeD} in terms of \texttt{takeC}. Here is a first attempt.
\begin{lstlisting}[language=Curry]
takeD' :: (Approx a, Data a) => Int -> T (List a) -> List a -> Tick (T (List a))
takeD' xsT ysD |  xsTD <~ xs
               && takeC n xsTD =:= Tick (ysD, c)
               =  Tick (xsTD, c)
  where xsTD, c free
\end{lstlisting}
In English: \texttt{takeD n xs ysD} finds some \texttt{xsD} and \texttt{c} such that \texttt{xsD} approximates \texttt{xs} and \texttt{takeC n xsD} evaluates to \texttt{(ysD, c)}. Strictly speaking, \texttt{takeD} ought to also return an demand on the argument \texttt{n}; however, we have defined ``approximation'' in \texttt{Int} to just be equality, so this would serve no practical purpose.

The problem with \texttt{takeD'} is that it must \emph{guess} a valid input demand, which performs very poorly in our experience. We can do better by \emph{generating} valid input demands.
\begin{lstlisting}[language=Curry]
takeD :: Approx a => Int -> T (List a) -> List a -> Tick (T (List a))
takeD n xsT ysD | takeC n xsTD =:= Tick (ysD, c)
                = Tick (xsTD, c)
  where xsTD = approx xsT
        c free
\end{lstlisting}
Provided that \texttt{approx} is implemented correctly (\ie\ \texttt{approx xsT} evaluates precisely to all \texttt{xsTD} such that \texttt{xsTD <\char`\~ xsT} evaluates to \texttt{True}), \texttt{takeD} is equivalent to \texttt{takeD'}.

We can exercise our implementation by verifying that taking a length-\(0\) prefix places no demand on the input list.
\begin{lstlisting}[language=Curry]
> takeD 0 Undefined Nil :: Tick (Thunk (List Int))
(Tick (Undefined,1))
\end{lstlisting}
By contrast, taking a length-\(1\) prefix places \emph{some} demand on the input list, even if it is empty.
\begin{lstlisting}[language=Curry]
> takeD 1 (Thunk Nil) Nil :: Tick (T (List Int))
(Tick ((Thunk Nil),1))
\end{lstlisting}
What happens if we provide an output demand that corresponds to multiple valid input demands?
\begin{lstlisting}
> takeD 1 (Thunk (fromList [1])) (1 :~ Undefined) :: Tick (T (List Int))
(Tick ((Thunk (:~ 1 Undefined)),1))
(Tick ((Thunk (:~ 1 (Thunk Nil))),1))
\end{lstlisting}
The least result is \texttt{Thunk (1 :~ Undefined)}, so this is the ``true''
result in demand semantics. If we want \emph{only} the least result, we can use
Curry's \emph{search tree}
functionality~\cite{DBLP:journals/jflp/BrasselHH04}. The \texttt{someValueWith}
function defined in \texttt{Control.Search.SearchTree} collapses a
nondeterministic computation into a deterministic one according to a given
\emph{search strategy}, which tells Curry how to navigate a tree of
nondeterministic computations. Since we have arranged our definitions so that
the less-defined result is always on the left branch of the search tree, we can
always find the least result via a depth-first search.
\begin{lstlisting}
> someValueWith dfsStrategy $ takeD 1 (Thunk (fromList [1])) (1 :~ Undefined)
    :: Tick (T (List Int))(T (List Int))
(Tick ((Thunk (:~ 1 Undefined)),1))
\end{lstlisting}

What else? A classic fact about lazy evaluation is that one can efficiently find the \(n\) smallest elements in a list by first sorting it and then taking a length-\(n\) prefix (provided that one uses a sufficiently lazy sorting algorithm). To test this, we first define insertion sort in clairvoyance semantics (\texttt{insertionSortC}).

\begin{lstlisting}[language=Curry]
insertC :: Ord a => a -> List a -> Tick (List a)
insertC x ys = do
  tick
  fcase ys of
    Nil -> do
      ys' <- nilC
      return (x :~ ys')
    y :~ ysT' ->
      if x <= y then do
        ysT <- thunk (return ys)
        return (x :~ ysT)
      else do
        ysT'' <- with ysT' (insertC x)
        return (y :~ ysT'')

insertionSortC :: Ord a => List a -> Tick (List a)
insertionSortC xs = do
  tick
  fcase xs of
    Nil -> return Nil
    x :~ xsT' -> do
      ysT' <- with xsT' insertionSortC
      ys' <- force ysT'
      insertC x ys'
\end{lstlisting}
Next, we define \texttt{nminC} as a composition of \texttt{takeC} and \texttt{insertionSortC}, along with its demand-semantics counterpart \texttt{nminD}.
\begin{lstlisting}[language=Curry]
nminC :: Ord a => Int -> T (List a) -> Tick (List a)
nminC n xsT = takeC n =<< with xsT insertionSortC

nminD :: (Ord a, Approx a) => Int -> T (List a) -> List a -> Tick (T (List a))
nminD n xsT ysTD | nminC n xsTD =:= Tick (ysTD, c)
                 = Tick (xsTD, c)
  where xsTD = approx xsT
        c free
\end{lstlisting}
Now, how much does it cost to sort a \(3\)-element list?
\begin{lstlisting}[language=Curry]
> insertionSortDG (fromList [3, 2, 1]) (fromList [1, 2, 3]) :: Tick (List Int)
(Tick ((:~ 3 (Thunk (:~ 2 (Thunk (:~ 1 (Thunk Nil)))))),10))  
\end{lstlisting}
If we demand the entire result, we incur a cost of \(10\) ticks. What if we just want the first element?
\begin{lstlisting}
> someValueWith dfsStrategy $ nminDG 1 (Thunk (fromList [3, 2, 1])) (fromList [1])
    :: Tick (T (List Int))
(Tick ((Thunk (:~ 3 (Thunk (:~ 2 (Thunk (:~ 1 (Thunk Nil))))))),9))
\end{lstlisting}
The resulting computation only costs \(9\) ticks.

\subsection{Performance}

\begin{figure}[t]

  \caption{The runtime of
    \cdc{insertionSortD}.}\label{fig:insertionSortD_runtime}
\end{figure}

Although our translation provides a convenient way to compute demands, a
question remains about how it performs relative to hand-written demand
functions. To test this, we ran \texttt{insertionSortD} on completely
out-of-orders lists with sizes ranging from \(1\) to \(100\), demanding the full
result each time (\cref{fig:insertionSortD_runtime}).

Asymptotically, \texttt{insertionSortD} appears to run in \(O(n^3)\) time. This
is equivalent to the hand-written version, which, in the worst case, must call
the pure \texttt{insertionSort} function \(n\) times. However, the constants are
much worse: \texttt{insertionSortD} takes more than \(6\) seconds on a
\(100\)-element list, while the hand-written version is fast enough that its
runtime cannot be reliably measured.
