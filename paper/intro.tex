\paragraph{Lazy cost analysis.}
In lazy evaluation, a computation is driven by its demands, performing only
the operations required to compute a final result~\cite{launchbury1993}. Lazy
evaluation enables functional programmers to write compositional code with
comparable or potentially better performance~\cite{fp-matters}. However, because
computations in lazy evaluation are on demand, out of order, and interleaved
with other computations, analyzing the ``performance'' of a lazy functional
program becomes much more challenging, as the analyzer needs to reason about
mutable heaps and cannot consider a function in isolation.

Various ideas have been proposed to tackle this challenge, which we can divide into roughly three different approaches. The first approach,
represented by work on Iris$^{\$}$~\cite{iris-credit,iris-thunk}, deal with
mutable heaps directly using tools like separation
logic~\cite{separation-logic}. \lai{Need a comment here to mirror the comment about Liquid Haskell} The second approach, represented by
LiquidHaskell~\cite{liquidate,liquid-okasaki}, uses a graded monad proposed by
Danielsson~\cite{danielsson-08} to track computation cost. However, this
approach needs to deal with sharing manually \lai{Should state why this is an issue, or else the thought feels unfinished}. The third and final approach instead utilizes alternative semantics that are equivalent to lazy evaluation in
terms of computation
cost~\cite{bjerner1989,clairvoyant,forking-paths,demand-semantics}. In contrast
to the natural semantics of lazy evaluation~\cite{launchbury1993}, these
semantics reify computation cost in pure and eager semantics, so one needs not be concerned with mutable heaps, sharing, or our-of-order executions.

\paragraph{Clairvoyance semantics and demand semantics.}
In this paper, we examine two semantics studied in the third
approach, namely the clairvoyance semantics proposed by Hackett and
Hutton~\cite{clairvoyant}, and the demand semantics proposed by Bjerner and
Holmstr{\"{o}}m~\cite{bjerner1989}.

The clairvoyance semantics builds on the observation that, for the sake of
analyzing computation cost, it only matters \emph{if} a computation cost is
incurred, not \emph{when}. Therefore, the clairvoyance semantics evaluates terms
eagerly, but every time it runs into a lazy operation, it makes a
\emph{nondeterministic} choice of evaluating a computation or skipping it. Thus, a lazy program's cost is represented as a walk through the resultant tree of possible execution paths, mimicking the choices to evaluate or choose not to evaluate terms in the original program.

The demand semantics, on the other hand, assumes that the demand on the output
of a function is given as a parameter, in addition to the function's input.
The demand semantics can then run ``backward'' to calculate the minimal input
demand. In this semantics, then, a lazy program's cost is represented by this ``backward'' function, which calculates the amount of the input consumed to compute the output demand. \lai{Not 100\% complete - the second function is cost-equivalent, and that cost is the lazy function's cost. These two semantics were proposed independently, but it turns out that they
correspond to two directions of the same functional logic program. Indeed,
we can translate a given lazy functional program into a functional
logic program that uses \emph{choice} to simulate the clairvoyance semantics. If
we then add the desired input\lai{Did we mean output here?} demand(s) as \emph{free variables}, the new functional
logic program simulates the demand semantics. In this paper, we demonstrate this
connection both in theory and in practice.

In particular, we make the following contributions:

\begin{itemize}
  \item We propose and formalize a mechanical way of translating functional
        programs to functional logic programs, producing the clairvoyance
        and demand semantics~(\cref{sec:translation}).
  \item We formally prove that our translation is correct with respect to both
        the clairvoyance semantics and the demand semnatics. All theorems
        and proofs are mechanized in Agda~(\cref{sec:equiv}).
  \item We conduct a number of case studies by manually translating classical
        lazy Haskell programs\ly{TODO:\ replace these with exact names when we

        programs based on our translation strategy~(\cref{sec:case-study}).
