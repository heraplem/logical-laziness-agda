\section{The Translation}\label{sec:translation}

In this section, we define two languagues, a base language \(\LB\) that
corresponds a simple functional language~(\cref{subsec:base-lang}) and a logic
language $L$ that corresponds to a functional logic
language~(\cref{subsec:logic-lang}). We first develop a \emph{clairvoyance
  translation} strategy that translates a program in \(\LB\) to a program in
\(\LL\) that models the clairvoyance
semantics~\cite{clairvoyant,forking-paths}~(\cref{subsec:clairvoyance-translation}).
We then develop a \emph{demand translation}, which models the demand
semantics~\cite{bjerner1989,demand-semantics}, as a thin wrapper of the
clairvoyance translation~(\cref{subsec:demand-translation}). Finally, we show
how such a translation strategy works by applying it to the example of
\texttt{take} and \texttt{append} discussed in \cref{sec:motivating-example}.

We prove that this translation strategy is correct with respect to the
clairvoyance semantics and the demand semantics in Agda, but we defer details of
the correctness theorem, its proof, and the Adga development to
\cref{sec:equiv}.

\subsection{The Base Language \(\LB\)}\label{subsec:base-lang}

We show the syntax of \(\LB\) in \cref{fig:syntax-base}. The base language is a
simple typed calculus with booleans, lists, and lazy thunks. Its terms include
variables, let-bindings, conditionals, and recursions based on $\tfoldrZ$. In
addition, it contains the explicit \( \tlazyZ \) and \( \tforceZ \) for wrapping
a computation in a lazy thunk and forcing a computation in a thunk,
respectively. The \(\TThunkZ\) datatype represents thunks in lazy evaluation: a
thunk only evaluates the first time it is \( \tforceZ \)d, then it remains that
value. Finally, we have an explicit \( \ttickZ \) term to indicate incurring one
unit of computation cost. These explicit operators decouple our analysis from
any particular evaluation model.

We do not have functions or general recursions in \(\LB\). This is because
(1)~the demand semantics does not support those
features~\cite{bjerner1989,demand-semantics}, and (2)~most functional logic
programming languages (except Verse~\cite{verse}) only support higher-order
functions via defunctionalization~\cite[Section 3.3]{curry-lang}.\stl{PAKCS uses
defunctionalization, kics2, mcc, rice, curry2go, and sprite do not.
There's nothing inherently in functional logic programming that prevents us from using closures.}

Most of the typing rules for \(\LB\) are standard, so we omit them. We show the
typing rules for thunks and computation costs in \cref{fig:typing-base}.
Notably, our lists are lazy: the cons of lists $\tcons{t_1}{t_2}$ takes a term
$t_1$ of type $A$ and a term $t_2$ of type $\TThunk{(\TList{A})}$, so the tail
of a list must always be wrapped in a thunk. Similarly, the ``function''
argument to $\tfoldrZ$ always assumes that its second paramter is wrapped in a
thunk.

\paragraph{Evaluation semantics.}
We can give language \(\LB\) a denotational semantics $\EE{t}{\gamma}$ for any
term $t$ under an evaluation context $\gamma$ by simply ignoring all
lazy-evaluation operators or computation cost:
$$\EE{\tlazy{t}}{\gamma} = \EE{\tforce{t}}{\gamma} = \EE{\ttick{t}}{\gamma} = \EE{t}{\gamma}$$

We do not need to model the natural semantics of \(\LB\) because prior works
have established equivalence in terms of computation cost between natural
semantics and clairvoyance semantics~\cite{clairvoyant}, and between
clairvoyance semantics and demand semantics~\cite{demand-semantics}. We discuss
more details of those semantics in \cref{sec:equiv}.

\subsection{The Logic Language $L$}\label{subsec:logic-lang}

We show the syntax of \(\LL\) in \cref{fig:syntax-logic}. Relative to \(\LB\),
\(\LL\) has some new types: a unit type \(\TUnit\), natural numbers \(\TNat\),
and product types \(\TProd{A}{B}\). 
\ifextended
We need the natural number type to model
computation costs, and we need product types to return computation results along
with costs. Since we are going to model demand semantics, we also need products
to model evaluation contexts, and we need the unit type to model \emph{empty}
contexts.
\else
We need natural numbers and products to represent computation costs. 
\fi
In addition, we replace the \(\TThunkZ\) type with a \(\TLazyZ\) type, which can
be either \(\tundefined\) or a \(\tresult{v}\) for some \(v\). We use this type
to represent if a computation is evaluated in the clairvoyance translation and
if a computation is demanded in the demand translation.

Terms of \(\LL\) include introduction and elimination forms for all new types.
We have no need for arbitrary functions on natural numbers, so we include only
literals and addition. We also have constructs for logic programming: logic
variables~(\(\tfreeZ\)), nondeterministic choice~(\(\tchooseZ\)), and
failure~(\(\tfail\)). Note that logic variables must be annotated with their
types in order to ensure deterministic typing. Finally, we have a Boolean
operator \(\tleZ\), which indicates whether its left-hand operand lies below its
right-hand operand in the order of approximations.

We define a simple functional logic language \(\LL\) instead of using an
existing formalization of one specific functional logic
language~(\eg~Curry~\cite{curry-lang,curry-monadic-semantics}, the Verse
calculus~\cite{verse}) to keep our approach generally applicable.\ly{Is there a
  particular formalization from a prior work that we are similar to?}

\paragraph{Derived terms in \(\LL\).}
We intend to use \(\LL\) to implement functional logic programs that ``carry''
the computation result and its cost as a product. To support simpler
manipulation over the product type, we implement some derived term constructs in
\(\LL\) that are shown in \cref{fig:logic-derived}. We define a term \treturn{t}
that wraps $t$ with a computation cost of 0; \tdo{x}{t_1}{t_2} chains two
computational terms $t_1$ and $t_2$ together, and accumulates their computation
costs; \tfoldM{x_1}{x_2}{t_1}{t_2}{t_3} chains computations in a list together,
and accumulates all the computation costs.\ly{I'm not sure if I understand
  \ttranspose{t}. Nicholas, can write a sentence about it?} In addition, we
define an \tassert{t_1}{t_2} operation that only continue computation if $t_1$
holds. We show all the typing rules related to these derived terms in
\cref{fig:logic-derived} as well. Readers who are familiar with monads might
recognize that \texttt{M} is a writer's monad~\cite{moggi-monad,wadler-monad}.

We define a translation \(\transC{-}\) from \(\LB\) to \(\LL\) that simulates
the clairvoyance semantics in \cref{fig:transC}. The translation is essentially
a monadic translation~\cite{moggi-monad,malias,wadler-monad} and is inspired by
Li \textit{et al.}'s work on the clairvoyance monad~\cite{forking-paths}: values
and variables are translated using \texttt{return}. The \texttt{let}-bindings
and \texttt{if} expressions are translated using \tdo{\cdot}{\cdot}{\cdot}. When
the term in \(\LB\) is a \tfoldrZ, we translate it to the derived term construct
\tfoldMZ.

The key for implementing clairvoyance semantics is in $\transC{\tlazy{t}}$ and
$\transC{\tforce{t}}$. When the orginal term is $\tlazy{t}$, we use the
nondeterministic operator \texttt{?} to either skip the inner term's
evaluation~(\(\treturn{\tundefined}\)), or compute the inner term and wraps the
result inside \tresultZ. When the term is $\tforce{t}$, we first evaluate \(t\)
and pattern match of the result $y_1$. If $y_1$ contains a $\tresult{y_2}$, we
return it; otherwise, we directly fail this computation branch---note that
\tfail{} only terminates the current nondeterministic branch, so other branches
that contain a \tresultZ{} will continue.\ly{What about ticks?}

\subsection{The Demand Translation}\label{subsec:demand-translation}

We now define another translation \( \transD{t}{\Gamma} \) from \( \LB \) to
\( \LL \) that simulates the demand semantics, shown in
\cref{fig:demand-translation}. Unlike the clairvoyance translation, the typing
context \(\Gamma\) in \( \LB \) is also a parameter to the translation. This is
because we need to introduce new free variables with types corresponding to
types in \( \Gamma \). This is consistent to the demand translation of Xia
\textit{et al.}~\cite{demand-semantics}.

\begin{figure}[t]
  \[
    \begin{array}{rl}
      \transD{t}{x_1 : A_1, \ldots, x_n : A_n} = &\tlet{x'_1}{\tfree{A_1}}{\relax} \\
                                                 &\tassert{\tle{x'_1}{x_1}}{\relax} \\
                                                 &\multicolumn{1}{c}{\vdots} \\
                                                 &\tlet{x'_n}{\tfree{A_n}}{\relax} \\
                                                 &\tassert{\tle{x'_n}{x_n}}{\relax} \\
                                                 &\tlet{u}{\transC{t'}}{\relax} \\
                                                 &\tassert{\teq{x}{\tfst{u}}}{\relax} \\
                                                 &\tpair{\texttt{(\( x'_1 \),\ \( \ldots \),\ \( x'_n \))}}{\tsnd{u}} \\
      \multicolumn{2}{c}{\text{where \( t' = t[x'_1/x_1, \ldots, x'_n/x_n] \).}}
    \end{array}
  \]
  \caption{The demand translation.}\label{fig:demand-translation}
\end{figure}

In addition, we define an operation \( \verts{-} \) that turns contexts into

\begin{theorem}
  If \( \TB{\Gamma}{t}{A} \), then \( \TL{\Gamma, x : A}{\transD{t}{\Gamma}}{\TM{\verts{\Gamma}}} \).
\end{theorem}
